Bug #1 (found here, fixed): a dark-seeded palette on a "light" page was unreadable

The page wrapper (.djp-page) never painted the active palette's own background — only data-page-tone="dark" had a rule, and it painted the brand colour, never the palette's "paper" tone. "Ember" seeds a DARK paper (near-black) with a light ink (white), so on this camp page — theme.tone: "light" — the wrapper stayed the host's own unpainted white, and any section relying on that page background (the FAQ) rendered Ember's white ink text on that white ground: invisible questions. Five of the twelve presets are dark-seeded and were affected the same way. Fixed in commit 54ed0449: the wrapper now paints the palette's own background/foreground pair, so a dark-seeded palette reads as a dark page — correctly — even when "Tone" is still set to "Light". Toggling "Tone" to "Dark" (09) does something different from what it would on a light-seeded palette: it paints the page's brand colour (a red) over those same sections instead of the palette's near-black paper, since the tone override always wins over the palette's own ground.

Bug #2 (found here, fixed): brand colour was never proven readable as text on the page itself

Originally reported here as one narrow symptom — the sales page's pricing section rendered its heading ("One block, one price") and price ("$1,200") in dark navy ink on a near-black card. Commit 3954dde7 fixed the price alone. Re-verifying afterwards found the SAME defect still live on the section's own heading, which pointed at the real shape of the bug: brand was only ever guaranteed readable as a BACKGROUND (paired with brandInk), never as TEXT painted directly on the page's own ground — which is exactly how .djp-hd, .djp-plan-price and .djp-proof-value use it outside an explicitly-toned band.

Two follow-up commits closed it properly. a4e37d25 swept every other element with the same hardcoded-brand pattern (icons, eyebrows, form required-marks, the FAQ disclosure marker) into the existing tone-contrast mechanism. 5d7bbcfb then measured brand-vs-paper across all twelve presets and found it was never a near-miss on one preset — four of twelve failed AA outright (ink 1.10:1, midnight 1.88:1, steel 2.19:1, plum 2.74:1; even the best, ember, cleared the 3:1 floor by only 0.01), and added a derived brandOnPaper token that guarantees 4.5:1 against both paper and surface for all twelve. Verified directly on the live pages above: the sales pricing heading and the camp FAQ heading both now read clearly, with no hand edit.

Bug #3 (found by a whole-branch review, fixed): the same pattern, a fourth time — accent

Same shape again, this time for --accent rather than --primary: .djp-eyebrow, the bullet/pricing/form-proof checkmark icons, the required-field mark, the FAQ toggle glyph and the quiz progress bar all painted accent directly as TEXT on a default (untoned) section's own ground — never proven safe there. Measured: ink 1.11:1, steel 1.40:1, midnight 2.47:1, against a 4.5:1 floor. Fixed in 0f2d2087 with an accentOnPaper token, the same derivation as brandOnPaper above. Visible on 06: the bullet icons in "Why the last three years went nowhere" were an unreadable near-black smudge on the previous capture and are now a warm, legible brown.

This is the fourth time this exact class of bug shipped, and the reason it kept getting past a green suite is named directly in 0f2d2087's own commit message: render.test.ts had a hand-maintained table declaring --accent "legal" on --background/--surface as a scope-invariant fact — true for the app's four fixed default themes, false for every one of the twelve derived palettes. Even the PRIOR fix wave added --primary-on-paper to that same table without asking why --accent was sitting in it unproven. The table is gone now, replaced by a check that measures the real palettes directly instead of trusting a list of pairs someone once believed were safe.

What this does and does not prove

  • Real variety, unprompted about design mechanics. Each brief named only mood, audience and content priorities — never a palette name, a recipe name, or a theme key. The model chose "ink" (near-black/red) for the sales page, "ember" (red/green) for the camp page, and left the waitlist page on defaults; it chose a 6-section capture-style layout for the waitlist and 9-section long-form layouts for the other two. None of that was dictated.
  • The light/dark pairs are a control, not a third design. Toggling "Tone" in the Page design panel is a plain, non-AI edit — the same op path a click-to-edit uses. It proves the control is reachable by hand and that every page repaints correctly in both tones; it is not a second example of the AI choosing a look.
  • The waitlist page under-uses the new knobs. Its stored theme only sets tone, accent and radius — font, density, width and rhythm were left unset and fall back to defaults. That is a legitimate choice for a deliberately plain, "nothing loud" brief, but it means one of the three pages is a weaker demonstration of the new controls than the other two.
  • Real credits were spent. Three first drafts plus each page's own review/self-critique pass — visible mid-run in the camp builder screenshot — are genuine model calls against the dev clone, not fixtures.
  • The sales page's review pass outran this script's own wait. The capture script waited for the stored document to stop changing for 20 seconds before treating a first draft as final — matching capture-ai-colour-turn.mjs's "wait on the document, not a spinner" rule. For the sales page that was not long enough: the review/self-critique pass kept revising it afterwards (the pricing copy and price changed after the first capture), so 05/06 were re-shot once the document was confirmed to have stopped changing for good. The waitlist and camp pages did not drift.
  • This set went through four re-capture passes as fixes landed — never a rebuild, always the same stored documents. Pass 1: 54ed0449/3954dde7 (camp's page wrapper, sales's price) — re-shot 05-10. Pass 2: a4e37d25/5d7bbcfb (the brand-on-paper sweep) — re-shot 05, 06, 08, and 10 again, as a clean before/after instead of a "partially fixed" caption. Pass 3: 0f2d2087 (the matching accent-on-paper sweep, instance #4 of the same class) — re-shot 06 only, once probing confirmed it was the sole page whose rendered colours actually moved. Every pass, every one of the nine page PNGs was checked, not just the ones expected to move: verified by probing computed color/background-color on the live DOM (.djp-page, .djp-hd, .djp-plan-price, .djp-eyebrow, .djp-ic and more) and by opening a fresh screenshot of every route side by side with the committed one. 01-05, 02/03, 07/09 and 10 stayed as they were across pass 3 specifically: sales's as-built page has no default-tone section for the accent fix to reach; camp's only default-tone section (its FAQ) has no eyebrow, icon or required-mark for it to touch; waitlist has no active palette; and the pricing card in 10 uses icons that were already fixed a pass earlier (they're on a muted-toned section, not default).
