Bug #1 (found here, now fixed): a dark-seeded palette on a "light" page was unreadable

Screenshots 07-09 above were re-captured after this landed. The page wrapper (.djp-page) never painted the active palette's own background — only data-page-tone="dark" had a rule, and it painted the brand colour, never the palette's "paper" tone. "Ember" seeds a DARK paper (near-black) with a light ink (white), so on this camp page — theme.tone: "light" — the wrapper stayed the host's own unpainted white, and any section relying on that page background (here, the FAQ) rendered Ember's white ink text on that white ground: invisible questions. Five of the twelve presets are dark-seeded and were affected the same way. Fixed in commit 54ed0449: the wrapper now paints the palette's own background/foreground pair, so a dark-seeded palette reads as a dark page — correctly — even when "Tone" is still set to "Light". Toggling "Tone" to "Dark" (09) now does something different from what it would on a light-seeded palette: it paints the page's brand colour (a red) over those same sections instead of the palette's near-black paper, since the tone override always wins over the palette's own ground.

Bug #2 (found here): the pricing section — partially fixed, not fully

Originally reported here: the sales page's pricing section (style.tone: "muted") rendered both its heading ("One block, one price") and its price ("$1,200") in dark navy ink on a near-black card — .djp-plan-price was hardcoded to color: var(--primary) with no override for a muted section, the same way accent/dark sections already had one. Commit 3954dde7 fixed the price by extending that same color: inherit treatment to .djp-plan-price on a muted tone — confirmed above, it is now white and reads clearly.

It did not fix the section's own heading. .djp-hd (every section heading in this design system) is separately hardcoded to color: var(--primary), and only accent/dark tones get a color: inherit override for it — muted still does not. So "One block, one price" is still dark navy on a near-black card, on the AI's own live page, right now, with no hand edit involved. This is the same root cause as bug #1 above (a hardcoded token never proven against a tone/palette combination it can actually meet), recurring in a different element. Reported, not fixed — see task-12-report.md for the exact lines.

What this does and does not prove

  • Real variety, unprompted about design mechanics. Each brief named only mood, audience and content priorities — never a palette name, a recipe name, or a theme key. The model chose "ink" (near-black/red) for the sales page, "ember" (red/green) for the camp page, and left the waitlist page on defaults; it chose a 6-section capture-style layout for the waitlist and 9-section long-form layouts for the other two. None of that was dictated.
  • The light/dark pairs are a control, not a third design. Toggling "Tone" in the Page design panel is a plain, non-AI edit — the same op path a click-to-edit uses. It proves the control is reachable by hand and that every page repaints correctly in both tones; it is not a second example of the AI choosing a look.
  • The waitlist page under-uses the new knobs. Its stored theme only sets tone, accent and radius — font, density, width and rhythm were left unset and fall back to defaults. That is a legitimate choice for a deliberately plain, "nothing loud" brief, but it means one of the three pages is a weaker demonstration of the new controls than the other two.
  • Real credits were spent. Three first drafts plus each page's own review/self-critique pass — visible mid-run in the camp builder screenshot — are genuine model calls against the dev clone, not fixtures.
  • The sales page's review pass outran this script's own wait. The capture script waited for the stored document to stop changing for 20 seconds before treating a first draft as final — matching capture-ai-colour-turn.mjs's "wait on the document, not a spinner" rule. For the sales page that was not long enough: the review/self-critique pass kept revising it afterwards (the pricing copy and price changed after the first capture), so 05/06 were re-shot once the document was confirmed to have stopped changing for good. The waitlist and camp pages did not drift.
  • 07-09 and 05/06 were re-captured after two stylesheet fixes landed (bugs #1 and #2 above) — same stored documents, same builder settings, only the CSS changed. 10 was re-shot to show the current, still-partial state rather than leave a fixed screenshot captioned as broken, or a broken one captioned as fixed. 01-04 and 02/03 (waitlist) were checked and confirmed unaffected — waitlist has no active palette and no pricing section, so neither fix's gate applies to it; verified by probing .djp-page's computed background directly, not assumed.
