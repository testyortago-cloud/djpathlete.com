# Team Image Submissions — Design

**Date:** 2026-05-14
**Status:** Approved for implementation planning
**Scope:** Extend the editor → admin team-video review workflow to accept photo submissions (single images and carousels), with Claude vision-generated draft captions on send-to-Content-Studio.
**Author:** Claude (via brainstorming) + Darren Paul
**Related:**
- [2026-04-24-content-studio-multimedia-design.md](./2026-04-24-content-studio-multimedia-design.md) — Multimedia umbrella (images/carousels already in Studio)
- [2026-05-03-team-video-review-workflow.md](../plans/2026-05-03-team-video-review-workflow.md) — Existing video review pipeline

---

## 1. Problem

Today the editor pipeline is video-only:

- `/editor/dashboard` exposes "Upload video" as the only submission affordance.
- `team_video_submissions` / `team_video_versions` store a single video file per version.
- Admin review (`/admin/team-videos/[id]`) renders `TeamVideoPlayer`; annotations are pinned to a video timestamp.
- "Send to Content Studio" creates a `video_uploads` row and queues `video_transcription`.

The Content Studio side already supports image and carousel post types (Phase 1+2 of the multimedia umbrella), with `media_assets`, `social_post_media`, and a working vision pipeline (`functions/src/image-vision.ts`). But there is no editor-facing way to submit photos for Darren's review, and no path from an approved photo submission into Content Studio.

The team should be able to submit photos through the same approval rhythm they already use for video clips. When Darren approves a photo set, it should land in Content Studio with draft captions per platform — generated by Claude vision — ready for him to tweak and schedule.

## 2. Goals

- Editors submit **1–10 photos per submission** (1 = single-image post, 2+ = carousel) through the existing editor surface.
- Admin reviews photos through the same review surface they use for videos (comments, revision requests, approval).
- On approval, "Send to Content Studio" creates a Content Studio draft post per enabled platform with `post_type='image'` or `'carousel'`, attaches the photos as `media_assets`, and queues Claude vision captioning per post.
- Captions are platform-aware (IG hashtag-heavy, LinkedIn longer-form, TikTok hook-first, Facebook conversational).
- Per-image `alt_text` populated on each `media_assets` row (accessibility + alt for IG/FB).
- Reuse existing primitives — versions, comments, status machine, Firebase storage — without forking a parallel pipeline.

## 3. Non-goals

- Story submissions through editor review. Stories already bypass the approval gate in Studio (per Phase 3 of the multimedia spec) and are admin-only.
- In-browser image editing (crop, filter, overlays). Editor submits raw photos; any compositing happens in Studio (e.g., AI quote cards) or before upload.
- Mixed-media submissions (a video + photos in one submission). One submission = one media kind.
- Reordering or annotation pins **inside** an image (free-form draw on a photo). Comments on photo submissions attach to "image index N", not to coordinates.
- Reusing photos across submissions. Each submission owns its own `media_assets` rows; cross-submission asset reuse stays a Studio-side concern via `media_assets`.
- Background removal, format conversion (HEIC→JPEG), or auto-orient. Browser uploads JPEG/PNG/WebP and we trust the bytes.

## 4. Architecture

### 4.1 Data model

Today: `team_video_submissions` (1) → `team_video_versions` (N) → single file at `version.storage_path`.

After: a submission's `kind` discriminates the version's payload shape. Video versions are unchanged. Image-set versions store the bag of image files in a new join table.

**`team_video_submissions` — add `kind`:**

```sql
alter table team_video_submissions
  add column kind text not null default 'video'
    check (kind in ('video', 'image_set'));

create index team_video_submissions_kind_idx on team_video_submissions(kind);
```

The table keeps its name (`team_video_*`). A rename would touch dozens of files for no functional benefit. Treat the prefix as historical naming.

**`team_video_versions` — relax video-only assumptions:**

```sql
alter table team_video_versions
  alter column mime_type drop not null,           -- image_set versions use per-image mime types
  alter column size_bytes drop not null,          -- image_set versions sum across images
  alter column original_filename drop not null,   -- image_set versions have N filenames
  alter column storage_path drop not null,        -- image_set versions use a folder prefix instead
  add column image_count int
    check (image_count is null or (image_count >= 1 and image_count <= 10));
```

For an `image_set` version:
- `storage_path` is the folder prefix (`team-videos/<submissionId>/v<n>/`); individual images live below it.
- `mime_type`, `size_bytes`, `original_filename` are null; per-image values live in `team_submission_images`.
- `image_count` is the row count in `team_submission_images` for this version. Trigger-maintained.
- `duration_seconds` stays null (it already could be null for video versions before transcoding).

For a `video` version, all old columns continue to be populated; `image_count` is null. The `DROP NOT NULL` migrations are constraint relaxations only — existing video rows already have non-null values for those columns and stay that way.

**New table `team_submission_images`:**

```sql
create table team_submission_images (
  id                 uuid primary key default gen_random_uuid(),
  version_id         uuid not null references team_video_versions(id) on delete cascade,
  position           int  not null check (position >= 0 and position <= 9),
  storage_path       text not null,
  original_filename  text not null,
  mime_type          text not null check (mime_type in ('image/jpeg','image/png','image/webp')),
  size_bytes         bigint not null check (size_bytes > 0 and size_bytes <= 8388608),
  width              int,
  height             int,
  created_at         timestamptz not null default now(),
  unique (version_id, position)
);

create index team_submission_images_version_idx on team_submission_images(version_id);
```

8 MB cap matches IG's image size ceiling. PNG is allowed even though IG transcodes to JPEG — the transcode happens server-side, the editor doesn't need to know.

**Trigger to maintain `image_count`:**

```sql
create function sync_team_version_image_count() returns trigger as $$
begin
  update team_video_versions
     set image_count = (
       select count(*) from team_submission_images
        where version_id = coalesce(new.version_id, old.version_id)
     )
   where id = coalesce(new.version_id, old.version_id);
  return null;
end;
$$ language plpgsql;

create trigger team_submission_images_count
  after insert or update or delete on team_submission_images
  for each row execute function sync_team_version_image_count();
```

**`team_video_comments` — no schema change**

Annotations on image_set submissions reuse the existing `annotation` jsonb column. Convention: `{ "kind": "image_index", "index": 0..9 }`. The video annotation kinds (`pin`, `drawing`, `timecode`) remain valid for video submissions. The annotation `kind` discriminator is the only thing that varies.

The UI never renders an image-index annotation on a video, or vice versa, because the comment thread is scoped to a single submission whose `kind` is known.

### 4.2 Storage layout

Reuses the existing `team-videos/` Firebase bucket so there's one team-submission storage surface.

```
team-videos/
  <submissionId>/
    v1/
      <video-file>         # kind=video version
    v2/
      <video-file>
    --- or ---
    v1/
      0_<filename>.jpg     # kind=image_set version
      1_<filename>.jpg
      2_<filename>.png
```

`buildVersionPath` is extended:

```ts
export function buildImagePath(
  submissionId: string,
  versionNumber: number,
  position: number,
  filename: string,
): string {
  const safe = filename.replace(/[^a-zA-Z0-9._-]+/g, "_").slice(0, 120)
  return `${TEAM_VIDEO_PATH_PREFIX}/${submissionId}/v${versionNumber}/${position}_${safe}`
}
```

The `<position>_` prefix makes the storage layout self-documenting (you can tell carousel order at a glance) and avoids filename collisions when two slides share a name.

### 4.3 Editor flow

`/editor/dashboard` gains a single "**New submission**" button with a dropdown menu (Video / Photos), replacing the existing single "Upload video" button. The video path is unchanged. The photo path opens a new dialog: title, optional description, drag-drop zone for 1–10 images, drag-reorder thumbnails.

**Submit API:**

```
POST /api/editor/submissions/photos
body: {
  title: string,
  description?: string,
  images: Array<{
    filename: string,
    mimeType: 'image/jpeg' | 'image/png' | 'image/webp',
    sizeBytes: number,
    position: number,
  }>  // length 1..10
}

returns 201:
{
  submission: TeamVideoSubmission,    // kind='image_set'
  version: TeamVideoVersion,
  uploads: Array<{
    position: number,
    uploadUrl: string,                // signed Firebase v4 PUT URL
    storagePath: string,
    expiresInSeconds: number,
  }>
}
```

The browser then PUTs each image to its signed URL in parallel. Once all PUTs succeed, the browser calls:

```
POST /api/editor/submissions/[id]/finalize
```

which flips the submission status from `draft` to `submitted`. The finalize endpoint already exists for videos; it gains an early branch: for `image_set` submissions, it verifies every `team_submission_images` row has its corresponding Firebase object before transitioning status. A missing object means upload failed — return 409, the browser retries that PUT.

**Revision uploads** (after admin requests revision): editor opens the submission, picks "Upload revision". Same dialog as initial submit, defaults pre-filled from the latest version. Creates a new version with `version_number = max+1` and a fresh image set. Comments thread is unchanged; the previous version's images remain in storage for the audit trail.

### 4.4 Admin review surface

`ReviewSurface` reads `submission.kind` and switches between two viewers:

- **`kind='video'`** → existing `TeamVideoPlayer` + `DrawingCanvas` overlay, unchanged.
- **`kind='image_set'`** → new `ImageSetViewer`: a paginated carousel with thumbnails strip below, keyboard-nav (←/→), and "Image 3 of 7" affordance. No annotation canvas — comments pin to the active image's index via the comment editor.

**`CommentEditor` adaptation:** when `kind='image_set'`, the "pin to timestamp" button is replaced with "Pin to current image" which writes `annotation = { kind: 'image_index', index: <currentImageIndex> }`. The comment thread renders an "Image N" pill next to such comments and clicking it jumps the viewer to that image.

**`StatusActions`** (request revision / approve / send to studio) is unchanged in behaviour but its button labels stay generic ("Approve", "Request revision", "Send to Content Studio") — they already are.

**`TeamVideoTable`** (admin index) gets a kind badge ("Video" / "Photos") in the title cell, using the existing pill component. Filter by kind is deferred — we expect few enough rows that scanning works fine; revisit if volume grows.

### 4.5 Send-to-Content-Studio (image_set branch)

`POST /api/admin/team-videos/[id]/send-to-content-studio` is the existing endpoint. Current behavior:

```
submission.kind === 'video':
  1. createVideoUpload(...) from current version
  2. lockSubmission(...)
  3. createAiJob({ type: 'video_transcription', input: { videoUploadId } })
```

New branch:

```
submission.kind === 'image_set':
  1. Read team_submission_images for the current version, ordered by position
  2. For each image:
     a. Move the file from team-videos/ into the media-assets bucket
        (or: copy + leave original; safer audit, doubles storage. Default: copy.)
     b. INSERT media_assets row (kind='image', storage_path=new path, public_url,
        mime_type, bytes, width, height, created_by=admin)
  3. Read the platforms Darren has enabled (existing social_connections / preferences)
  4. For each enabled platform that supports image OR carousel:
     a. INSERT social_posts row with:
        - post_type='image' (if image_count===1) or 'carousel' (if image_count>=2)
        - platform=<platform>
        - approval_status='draft'
        - caption=''
        - source_video_id=null
     b. INSERT social_post_media rows for each media_asset at its position
        (the existing media_url mirror trigger populates social_posts.media_url from position 0)
     c. createAiJob({
          type: 'image_caption_generation',
          input: {
            socialPostId: <new post id>,
            platform: <platform>,
            mediaAssetIds: [<asset ids in order>],
          },
        })
  5. lockSubmission(...)  // submission → 'locked', same as today
  6. Return { socialPostIds: [...], mediaAssetIds: [...] }
```

The video branch returns `{ videoUpload }`. Add a top-level discriminator to the response so the caller doesn't have to guess:

```ts
type Response =
  | { kind: 'video'; videoUpload: VideoUpload }
  | { kind: 'image_set'; socialPostIds: string[]; mediaAssetIds: string[] }
```

**Why per-platform draft posts, not one shared draft:** captions diverge by platform character limits and conventions (IG ≤ 2200, TikTok hook-first, LinkedIn longer-form, FB conversational). Sharing one draft means Darren rewrites it 4 times. Per-platform drafts mean Claude does the platform-aware drafting once and Darren edits each in place. This mirrors how the video pipeline emits 6 draft captions today (one per platform).

**Why copy assets out of `team-videos/` into the media-assets bucket:** the editor pipeline and Studio pipeline have different retention/lifecycle policies. Editor submissions get deleted when an editor leaves; Studio assets must persist for the lifetime of any post that uses them. Copying decouples the two.

### 4.6 Claude vision captioning

A new AI job type `image_caption_generation` runs in the Firebase functions pipeline alongside `image_vision_analysis` (which already exists for alt-text + scene/object/hashtag analysis).

**Job input:**

```ts
{
  socialPostId: string,
  platform: 'instagram' | 'facebook' | 'tiktok' | 'linkedin',
  mediaAssetIds: string[],  // length 1..10, in carousel order
}
```

**Handler outline (`functions/src/image-caption-generation.ts`):**

1. Read each media_asset's signed URL via Firebase storage.
2. Build a single Anthropic messages call with all images as `image` content blocks plus a platform-specific system prompt.
3. Parse the JSON response: `{ caption: string, hashtags: string[], cta: string | null }`.
4. UPDATE the `social_posts` row's `caption` and `metadata.ai_generated_at = now()`.
5. Also queue (or inline-run) `image_vision_analysis` per asset for the alt-text — that pipeline already exists and populates `media_assets.ai_alt_text`.

**Platform-specific prompts** live in `functions/src/lib/image-caption-prompts.ts`:

```
INSTAGRAM:   hook (1 line) + body (2-4 lines) + 5-10 lowercase hashtags. Carousels:
             reference "swipe" or progression across slides. Tone: motivational, direct.
FACEBOOK:    conversational, 2-3 sentences, no hashtags, end with a question or CTA.
TIKTOK:      hook-first (≤ 60 chars), then short body, 3-5 hashtags. Mention what to
             look for if it's a carousel.
LINKEDIN:    professional tone, story arc, 3-6 sentences, 0-3 hashtags max.
```

All four prompts share a base system prompt establishing the brand (Darren Paul, performance/coaching) and constraints (no medical claims, no specific PRs without explicit input).

**Carousel handling:** all images go in one request. Claude sees the sequence and writes a caption that references it ("swipe to see the progression from setup to rep finish"). For single-image posts, Claude writes a caption rooted in that one image.

**Output validation:**
- Caption ≤ platform character limit (truncate with `…` if over).
- Hashtags must match `/^[a-z0-9_]+$/`, ≤ 30 chars each; invalid ones are filtered.
- If the model returns malformed JSON, the job retries once with `response_format` enforcement; second failure marks the job `failed` and leaves the post caption empty (Darren can write his own).

**Cost note:** Anthropic Sonnet 4.6 vision cost ≈ $0.01–0.03 per image for typical sizes. Worst case: 10 images × 4 platforms = 40 images processed per submission ≈ $0.40–$1.20. Acceptable per submission. The handler runs unconditionally — no env kill-switch; if billing ever needs an emergency cut-off, drop the Firebase function or revoke its `ANTHROPIC_API_KEY` secret.

**Idempotency:** the job sets `social_posts.metadata.image_caption_job_id`. Re-running for the same post is a no-op unless `force=true` is passed in the job input.

## 5. Feature flag

Gate the editor-facing UI and admin review branching behind `NEXT_PUBLIC_TEAM_IMAGES_ENABLED`. The migration and routes ship without the flag (no harm idle); the flag controls only the editor dashboard CTA and the admin review viewer switch. This lets the schema land in prod ahead of the UI for safe verification.

## 6. Testing strategy

**Unit (Vitest):**
- `team_submission_images` CRUD + image_count trigger.
- `buildImagePath` filename safety + length cap.
- `createSubmission` with `kind='image_set'`.
- Finalize-route image_set branch: rejects if any storage object is missing; succeeds when all present.
- Send-to-Content-Studio image_set branch: mocks `media_assets` insert + `social_post_media` insert + `createAiJob` for each platform. Asserts one post per enabled platform, correct `post_type`, correct media positions.
- Image caption prompt builder: snapshots the per-platform prompt template.
- Caption generation handler: mocks Anthropic vision; asserts caption written to post, hashtags filtered, character limit enforced.

**Component (Vitest + Testing Library):**
- `PhotoSubmitDialog` — drag-reorder, 1–10 file cap, type + size validation.
- `ImageSetViewer` — keyboard nav, thumbnail strip, image-index pin click jumps viewer.
- `SubmissionList` row badge (Video / Photos).
- `TeamVideoTable` kind badge.

**E2E (Playwright):**
- Editor submits a 3-image set → admin reviews, comments on image 2, requests revision → editor uploads a new 4-image set → admin approves → admin clicks Send to Content Studio → 4 posts created in Studio (one per enabled platform), each with `post_type='carousel'` and 4 media attachments.
- Single-image submission produces `post_type='image'` posts.

**Manual smoke:**
- Vision caption job actually runs against a real test photo and produces a reasonable IG caption.
- Anthropic budget check: a 4-image carousel × 4 platforms costs < $0.50.

## 7. Risks & mitigations

| Risk | Mitigation |
|---|---|
| Per-image upload PUTs partially succeed and submission is half-uploaded | Finalize endpoint verifies every `team_submission_images` row has its Firebase object before flipping to `submitted`; missing objects return 409 with the failing positions so the client can retry. |
| Image bytes exceed Anthropic vision context (large 4K photos × 10 carousel slides) | Cap per-image side at 1568px before sending to Claude (Anthropic's recommended max long edge); resize happens server-side in the caption handler, original asset is untouched. |
| Editor uploads HEIC from iPhone | Browser-side MIME check rejects with a clear message. Auto-conversion is out of scope. |
| Annotation `kind: 'image_index'` confuses video review code | Review code reads `submission.kind` and only renders annotations whose kind matches the medium. A defensive switch in the comment renderer skips orphaned kinds. |
| Vision captions hallucinate specific numbers ("squatted 405 lbs") | Prompt explicitly forbids unverifiable specifics. Captions default to descriptive + emotional language. |
| Per-platform draft posts × N platforms × N approved submissions clutter the pipeline board | Existing pipeline filters (status, platform) already handle this; image posts inherit the same filters. Pipeline lanes are status-bucketed, not platform-bucketed, so visual load is bounded by `draft` count regardless of fan-out. |
| Storage cost grows with image copying (team-videos → media-assets) | Median submission is < 5 MB; this is order-of-magnitude smaller than video storage already in play. Acceptable. |

## 8. Open questions (deferred)

- Should we eventually unify the storage buckets so we don't copy? Decision deferred to whenever a retention policy is formalized.
- Should approved photo submissions auto-fire send-to-Content-Studio (skip the admin click), like approved videos do? Today both still require the manual click. Keep parity.
- Quote-card generation from photos (text overlay on an approved image)? Studio already has the quote-card pipeline from video transcripts; extending it to photos is a separate spec.

## 9. Rollout

1. Land the migration (Phase A) — `kind` column, `team_submission_images` table, trigger, signed upload helpers, DAL. Verify schema in prod.
2. Land the editor + admin UI behind `NEXT_PUBLIC_TEAM_IMAGES_ENABLED=false` in prod, `=true` in preview (Phase B).
3. Land the send-to-Content-Studio image_set branch + caption job (Phase C).
4. Dogfood: Darren has a team member submit a real photo set → Darren approves → captions appear in Studio.
5. Flip prod flag.

Each phase produces its own implementation plan following this spec.
